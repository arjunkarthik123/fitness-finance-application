UHR-PER-01 &
Personalized Fitness Goals &
\textbf{Description:} The system shall allow users to configure fitness goals based on their personal fitness level and preferences.

\textbf{Rationale:} Users will possess different fitness capabilities and activity levels. Personalized goals encourage engagement while remaining achievable.

\textbf{Fit Criterion:} Users shall be able to modify daily and weekly fitness goals that will take effect the next time period.\\
\hline

UHR-PER-02 &
Customizable Notifications &
\textbf{Description:} The system shall allow users to configure which notifications they receive and how frequently they are delivered.

\textbf{Rationale:} Users have varying preferences regarding reminders and activity notifications.

\textbf{Fit Criterion:} Users shall be able to independently enable or disable workout reminders, portfolio updates, and achievement notifications.\\
\hline

UHR-PER-03 &
Customizable Privacy Settings &
\textbf{Description:} The system shall allow users to control the visibility of their fitness achievements, portfolio statistics, and leaderboard participation.

\textbf{Rationale:} Users have different privacy expectations and comfort levels regarding public sharing of personal information.

\textbf{Fit Criterion:} Users shall be able to independently configure visibility settings for all community-facing features that will take immediate effect.\\
\hline

UHR-PER-04 &
Customizable Competition Groups &
\textbf{Description:} The system shall allow users to customize the set of users with whom they share and compare fitness and portfolio progress.

\textbf{Rationale:} Users may have different comfort levels regarding competition and sharing personal achievements. Allowing users to select their competition group creates a more personalized and engaging experience where friends can motivate each other.

\textbf{Fit Criterion:} Users shall be able to choose between private, friends-only, and public, community-wide, leaderboard participation.\\
\hline

UHR-INT-01 &
Canadian Time Zone Support &
\textbf{Description:} The system shall automatically detect and utilize the user's local Canadian time zone when calculating daily goals, rewards, and streaks.

\textbf{Rationale:} Users may access the application from any Canadian province or territory.

\textbf{Fit Criterion:} Daily statistics and streak calculations shall correspond to the user's local device time zone.\\

UHR-LRN-01 & 
Minimal User Training & 
\textbf{Description:} The system shall enable first-time users to successfully use the application's core functionality without requiring formal training.

\textbf{Rationale:} The application targets users with varying expertises and should be intuitive for a broad audience.

\textbf{Fit Criterion:} At least 80\% of first-time users shall be able to synchronize fitness data, earn virtual currency, and purchase an investment asset without external assistance.\\
\hline

UHR-LRN-02 & 
Learning Curve of Financial Concepts & 
\textbf{Description:} The system shall present investment concepts in a manner that can be understood by users with little or no prior experience. 

\textbf{Rationale:} One of the system's primary goals is to educate users on financial investing. This means that all users, regardless of their prior financial experience, should be capable of learning and understanding the financial concepts presented.

\textbf{Fit Criterion:} During user testing, at least 80\% of first-time investors shall successfully complete their first virtual investment and view their portfolio's growth after one week without assistance.\\ 
\hline

UHR-LRN-03 & 
Learning Curve of Fitness Based Concepts & 
\textbf{Description:} The system shall present fitness concepts in a manner that can be understood by users with little or no prior experience. 

\textbf{Rationale:} One of the system's primary goals is to educate users on fitness and health related activities. This means that all users, regardless of their prior fitness experience, should be capable of learning and understanding the fitness concepts presented.

\textbf{Fit Criterion:} During user testing, at least 80\% of first-time participants in a new fitness activity shall successfully accomplish their set goal and view their health metrics after one week without assistance.\\ 
\hline

UHR-LRN-04 & 
Integrated Educational Assistance & 
\textbf{Description:} The system shall provide contextual learning resources within the application.

\textbf{Rationale:} In the event that users encounter unfamiliar fitness or financial terminology while using the platform, the system should offer immediate assistance to enhance their understanding so that users can quickly learn and pick up new concepts.

\textbf{Fit Criterion:} Users shall be able to access explanatory information for all core financial and fitness concepts directly from the screen where the concept appears.\\
\hline

UHR-LRN-05 & 
User Help Documentation & 
\textbf{Description:} The system shall provide readily accessible help documentation describing the application's functionality should any users require it.

\textbf{Rationale:} Users should be able to resolve common questions without external support.

\textbf{Fit Criterion:} A help section shall be accessible from the application's settings menu and include explanations of all major features. Support teams should receive zero inquiries about basic system functionality.\\

SEC-ACC-01 &
Authentication and Sessions &
\textbf{Description:} Users shall authenticate before accessing personal fitness data, portfolios, or transactions. The React Native client shall authenticate with the Spring API using secure token-based sessions.

\textbf{Rationale:} Authentication protects personal data and virtual assets from unauthorized access.

\textbf{Fit Criterion:} All protected API endpoints shall reject missing or invalid access tokens with HTTP 401. Access tokens shall expire within 60 minutes, with refresh or re-authentication required. \\
\hline

SEC-ACC-02 &
Role-Based Authorization &
\textbf{Description:} Role-based access control shall restrict users to their own records and limit administrative or evaluator access to authorized functions.

\textbf{Rationale:} Access restrictions prevent unauthorized modifications and cross-account data exposure.

\textbf{Fit Criterion:} JUnit security tests shall confirm that attempts by standard users to access or modify another user's records return HTTP 403 in all tested cases. \\
\hline

SEC-ACC-03 &
Fitness Integration Authorization &
\textbf{Description:} Flexin shall request only necessary read permissions for supported integrations, Android Health Connect and Garmin. Integration credentials shall be stored using secure, Android Keystore-backed storage.

\textbf{Rationale:} Secure credential handling protects external accounts and limits access to fitness data.

\textbf{Fit Criterion:} Integration tokens shall use Android Keystore-backed secure storage. No credentials, tokens, or secrets shall be committed to the project repository. \\
\hline

SEC-INT-01 &
Activity Validation &
\textbf{Description:} The Spring backend shall validate activity metrics and detect duplicate records, overlapping timestamps, and implausible activity values before awarding virtual currency.

\textbf{Rationale:} Validation prevents activity manipulation and unauthorized currency generation.

\textbf{Fit Criterion:} Automated tests shall confirm that duplicate or flagged implausible activity records are marked unverified and receive zero virtual currency. Sustained cadence above 250 steps per minute shall be flagged for verification. \\
\hline

SEC-INT-02 &
Ledger Consistency &
\textbf{Description:} All virtual currency operations, including rewards, trades, and dividends, shall use ACID-compliant MySQL transactions.

\textbf{Rationale:} Transactional consistency prevents duplicate rewards, negative balances, and partial updates.

\textbf{Fit Criterion:} Stress tests with 100 concurrent trade requests against one wallet shall verify that every operation commits consistently or rolls back completely, without partial state changes. \\
\hline

SEC-INT-03 &
Server-Side Valuation &
\textbf{Description:} The Spring backend and custom market engine shall determine asset prices, portfolio valuations, and currency calculations. The mobile client shall not control authoritative values.

\textbf{Rationale:} Server-side calculations prevent client manipulation of prices and balances.

\textbf{Fit Criterion:} Trade requests attempting to specify unauthorized execution prices shall be rejected with HTTP 400. \\
\hline

SEC-PRV-01 &
Health Data Protection &
\textbf{Description:} Sensitive personal information and fitness telemetry shall be protected through encryption in transit and at rest.

\textbf{Rationale:} Encryption protects confidential user information against unauthorized disclosure.

\textbf{Fit Criterion:} Client-server communications shall use TLS 1.3. Sensitive biometric data stored in MySQL shall be encrypted at rest using AES-256. \\

SEC-PRV-02 &
Opt-In Community Sharing &
\textbf{Description:} Leaderboard participation shall be opt-in. Users may share activity streaks and simulated portfolio returns using a chosen alias.

\textbf{Rationale:} Users should control whether their activity and simulated financial performance are visible to others.

\textbf{Fit Criterion:} Leaderboard sharing shall be disabled by default. Enabling it shall require explicit consent and disclose which pseudonymous information and statistics will be shared. \\
\hline

SEC-PRV-03 &
User Data Deletion &
\textbf{Description:} Users shall be able to request account deletion through the application settings, removing associated personal records.

\textbf{Rationale:} Users should retain control over their personal information and account history.

\textbf{Fit Criterion:} Personal health metrics, credentials, and fitness history shall be purged from the active database within 24 hours of a deletion request. Only appropriately anonymized transaction aggregates may be retained for auditing. \\

SEC-IMM-01 &
Injection Defense &
\textbf{Description:} The backend and database layer shall be protected against SQL injection, cross-site scripting (XSS), and command injection.

\textbf{Rationale:} Injection vulnerabilities could compromise database integrity and expose user information.

\textbf{Fit Criterion:} Database access shall use parameterized queries or prepared statements. Static analysis and security reviews shall identify zero unresolved high-severity injection vulnerabilities before release. \\
\hline

SEC-IMM-02 &
Rate Limiting &
\textbf{Description:} The Spring API shall limit request rates for authentication, trade submission, and activity synchronization endpoints.

\textbf{Rationale:} Rate limiting reduces brute-force attempts, automated abuse, and service overload.

\textbf{Fit Criterion:} A configured limit, initially 60 requests per minute per authenticated user or client IP, shall be enforced. Excess requests shall receive HTTP 429. Automated tests shall verify enforcement. \\
\hline

SEC-IMM-03 &
Client Environment Validation &
\textbf{Description:} The Android client shall detect supported indicators of rooted or otherwise untrusted environments and restrict sensitive functionality when tampering is detected outside developer builds.

\textbf{Rationale:} Compromised environments can increase the risk of credential exposure and activity manipulation.

\textbf{Fit Criterion:} In supported production configurations, detected root or tampering indicators shall trigger restrictions on community leaderboard access and virtual currency minting. Developer builds shall remain available for authorized testing. \\
\hline

\section{Cultural Requirements}

This section outlines the cultural requirements for the software system. Cultural requirements refer to the expectations and norms of the target user base, which may vary based on geographic location, language, social norms, and other cultural factors. These requirements ensure that the software is culturally sensitive and appropriate for its intended audience.

CUL-01 & 
Supports Canadian Languages & 
\textbf{Description:} The system shall present all user-facing functionality with the option to choose between English and French. 

\textbf{Rationale:} The application will initially be deployed strictly within Canada, where English and French are the country's official languages. 

\textbf{Fit Criterion:} All user-facing text shall be stored separately from application logic and be replaceable through a localization framework.\\ 
\hline

CUL-02 & 
Inclusive Financial Education & 
\textbf{Description:} The system shall provide financial education content that does not assume prior investing knowledge. 

\textbf{Rationale:} Users possess varying levels of financial literacy. The system seeks to educate users of all levels of financial literacy - including those who may have limited exposure to investing concepts. 

\textbf{Fit Criterion:} All investment-related terminology presented to users shall include a plain-language explanation accessible from within the application. All financial concepts shall be explained in simple, non-technical language to start, until the system deems the user has gained sufficient experience within the application. During user testing, a survey will be conducted to gather feedback on the clarity and understandibility of the financial education content - at least 80\% of users shall express great satisfaction with little to no problems understanding financial concepts.\\ 
\hline

CUL-03 & 
Inclusive Fitness Participation & 
\textbf{Description:} The system shall accommodate users with varying fitness levels by allowing personalized activity participation. 

\textbf{Rationale:} Users may differ significantly in age, physical ability, health conditions, and exercise experience. The application should promote participation regardless of fitness background. 

\textbf{Fit Criterion:} Users shall be able to participate in their preferred fitness activities while still gaining subsequent rewards.\\ 
\hline

CUL-04 & 
Culturally Neutral Educational Content & 
\textbf{Description:} The system shall present fitness and financial education content using culturally neutral language and examples (i.e. sample companies in the virtual market). 

\textbf{Rationale:} The Canadian population consists of individuals from diverse cultural, religious, and socioeconomic backgrounds. Educational content should be inclusive and broadly applicable. 

\textbf{Fit Criterion:} Educational content shall not require familiarity with a specific cultural background, religion, ethnicity, or region to be understood.\\ 
\hline

COMP-STD-01 & 
Android Platform Compliance & 
\textbf{Description:} The system shall comply with the Google Play Developer Program Policies. 

\textbf{Rationale:} The application is intended to be deployed on the Google Play Store as to be accessible on Android devices and as a result must conform to platform requirements. 

\textbf{Fit Criterion:} The application shall successfully pass all mandatory checks required for distribution through the Google Play Store.\\

COMP-STD-02 & 
Accessibility Compliance & 
\textbf{Description:} The system shall comply with WCAG 2.1 Level AA accessibility guidelines for user-facing functionality. 

\textbf{Rationale:} The system should offer a simple and delightful user experience that should be accessible to users with varying abilities (i.e. user's with colourblindness, hearing impairments, etc.).

\textbf{Fit Criterion:} All major user workflows shall satisfy WCAG 2.1 Level AA success criteria as evaluated using automated accessibility tools and manual testing.\\ 
\hline

COMP-STD-03 & 
TypeScript Coding Standards Compliance & 
\textbf{Description:} The frontend codebase shall comply with the Google TypeScript Style Guide. 

\textbf{Rationale:} Consistent coding standards improve maintainability, readability, and long-term project quality. 

\textbf{Fit Criterion:} All pull requests shall pass configured linting and formatting checks before merging into the main branch.\\ 
\hline

COMP-STD-04 & 
Java Coding Standards Compliance & 
\textbf{Description:} The backend codebase shall comply with the Oracle Java Code Conventions. 

\textbf{Rationale:} Standardized coding practices improve maintainability, code review effectiveness, and software quality. 

\textbf{Fit Criterion:} All pull requests shall pass configured linting and formatting checks before merging into the main branch.\\ 
\hline

COMP-STD-05 & 
Database Compliance & 
\textbf{Description:} The system shall store data in compliance with the MySQL Reference Manual and the SQL Standard (ISO/IEC 9075). 

\textbf{Rationale:} The project architecture relies upon MySQL as the primary relational database system. 

\textbf{Fit Criterion:} All schema definitions and queries will be tested to execute successfully on the supported MySQL version without compatibility warnings or errors.\\ 
\hline

COMP-STD-06 & 
Software Testing Standard Compliance & 
\textbf{Description:} The system shall undergo thorough and complete testing in accordance with the IEEE 29119 Software Testing Standard. 

\textbf{Rationale:} Consistent testing practices reduce defects and improve software reliability. The system will comply with this standard to provide a unified, process-driven framework for software testing.

\textbf{Fit Criterion:} All code merged into the main branch shall pass automated test execution in the CI/CD pipeline based on tests that were developed in accordance with the IEEE 29119 Software Testing Standard.\\ 
\hline

COMP-STD-07 & 
Information Security Compliance & 
\textbf{Description:} The system shall be designed in accordance with the security principles outlined in ISO/IEC 27001. 

\textbf{Rationale:} The application stores personal, financial-learning, and fitness-related information that must be protected against unauthorized access and disclosure. 

\textbf{Fit Criterion:} Security controls for authentication, access control, data storage, and data transmission shall align with ISO/IEC 27001 recommendations.\\
