\section{Workflow Plan}

The project workflow will be managed using Git, with our code and documentation hosted in our GitHub repository. Our \texttt{main} branch will serve as the primary codebase and will be the branch used for product deployments. To make contributions, developers are required to create branches directly from \texttt{main} and commit any initial changes to their respective branch.

\subsection{Branching Strategy}
We will utilize the following branch categories:
\begin{itemize}
    \item \textbf{feat (feature):} For development on a new feature.
    \item \textbf{bugfix:} For addressing and fixing identified issues within the codebase.
    \item \textbf{chore:} For code changes that support later development, such as refactoring or clean-up work.
\end{itemize}
Additionally, each branch must have a descriptive name that clearly indicates which issue in the GitHub project is being addressed.

\subsection{Issue Tracking and Project Management}
Issues will be categorized based on urgency, from \textbf{P0} (highest priority) to \textbf{P2} (lowest priority), ensuring that critical tasks are addressed promptly. 

The GitHub project board has been configured with the following setup: \textbf{Backlog} $\rightarrow$ \textbf{In Progress} $\rightarrow$ \textbf{Review} $\rightarrow$ \textbf{Closed}. As development progresses, it is the developer's responsibility to keep their assigned issues updated to maintain team visibility on project status.

\subsection{Pull Requests and CI/CD Pipeline}
As part of the new code added to a branch, developers are required to implement test cases to ensure adequate code coverage. Once code is committed, a Pull Request (PR) must be raised to merge the branch into \texttt{main}. 

Our Continuous Integration/Continuous Deployment (CI/CD) pipeline will enforce the following checks before a merge is permitted:
\begin{itemize}
    \item Automated testing and deployment checks.
    \item Linter execution to ensure code meets formatting and quality standards.
    \item Verification that the feature branch is up-to-date with \texttt{main}.
\end{itemize}

\subsection{Code Review Process}
In addition to passing all CI/CD checks, each PR requires a manual review and approval from at least one other group member. The PR comments section will be utilized to trace the iterative process of feedback and the subsequent code changes made to address said feedback.

\subsection{Pull Request Template Requirements}
Each PR must be directly linked to its corresponding issue in the GitHub Project board to maintain traceability. Furthermore, all PRs must adhere to a standardized template that includes:
\begin{itemize}
    \item A comprehensive summary of the changes made.
    \item Sample test cases and step-by-step instructions for the reviewer to verify the code.
    \item Screenshots of the updated UI (if the PR includes user interface modifications).
\end{itemize}

\section{Project Decomposition and Scheduling}

For aiding in documenting and tracing our project deliverables, we will be making use of two GitHub projects that will handle our code and our documentation deliverables. They are linked below: 

\begin{itemize}
    \item \textbf{Code Project:} \url{https://github.com/users/arjunkarthik123/projects/4/views/1}
    \item \textbf{Documentation Project:} \url{https://github.com/users/arjunkarthik123/projects/3}
\end{itemize}

Both projects are split into four sections: Backlog, In Progress, In Review, and Done. As the project progresses, we will come up with items that need to be addressed for both our documentation and later on our codebase. Whenever any team member thinks of an item that needs to be worked on, it will be added to the backlog of the respective projects. Depending on what the team decides, someone will be assigned the new issue, and whenever the person works on it, it will be under the In Progress section. In order to complete the deliverable, it first needs to be reviewed, hence the In Review section. For either the code or documentation, a pull request will be created and linked to the respective issue being addressed, and only when it gets approved will the issue move to the Done section. 

If the issues seem to be larger than anticipated, we will split up the issue using sub-issues and have them assigned accordingly. This is to ensure no single issue is too big to handle by one person alone.

\section{Expected Technology}

\subsection{Languages and Frameworks}
The application will be developed using the frontend React Native framework using Typescript as the coding language. 
React Native is very popular for mobile development and has become an industry standard. 
Typescript is a common language for frontend development (Rootstack, 2026). 
These are very popular choices with a large selection of open source libraries to be leveraged in the development process. 
We will also use the Figma to help the development team create UI mockups for testing and concept design.
\\The backend systems will consist of an SQL relational database through a MySQL server. 
A relational database for an app will allow the development team to keep more concise and organized records to reduce search and loading times for users. 
We will use the Java Spring.io framework to develop our API. We will be able to retrieve information through HTTP request formats (VMware Tanzu). 
This will provide the development an adequate level of security as we will need to deal with sensitive user information. 
\\The development team will use a Github repository to store the code and support the CI/CD process through development phases. The repository will create a code store for each member to reach and contribute to  throughout the process.
Our repository will utilize Copilot AI agents to ensure formatting consistency throughout the codebase. 
The development team will be using various linters such as ESLint (Arunodi, 2026) and the standard linters that come built into the IDE being used like VSCode, JetBrains Intellij and Visual Studio. 


\subsection{External Libraries}
Various external SDKs and APIs used to link to modern fitness devices.
\begin{itemize}
    \item Connect IQ (Garmin SDK): A major player in the fitness watch company has an open free SDK to be used for more accurate data collection and real time updates (https://developer.garmin.com/connect-iq/overview/).
    \item Strava API: A more recently popular application for runners to track data. This will allow us to connect to the strava tracking system for other more accurate data collection (https://developers.strava.com/).
    \item Health Connect API (Android Development Health API): Android provides an API for users to be able to retrieve health data to connect across applications easier (https://developer.android.com/health-and-fitness/health-connect).
\end{itemize}

\subsection{Technology and External Devices}
The application will rely on the device itself for its basic activity tracker. 
Any additional activity tracking devices like smart/fitness watches, standalone heart rate monitors, pedometers, etc. will be integrated utilizing the intended SDK or API provided by the manufacturer. 

\subsection{Testing}
The development team will use standard unit testing and system testing frameworks like JUnit. 
These tests will be manually prepared by the developers to test different features of the app mainly in the API. 
The development team will also utilize the automated testing framework called Detox. This is an automated react native testing framework that will provide another layer for validation and correctness (Maestro, 2026).

  \item If the team is struggling to decide between options (i.e. they cannot clearly 
  decide where to cast their votes), an unbiased third party will be involved to 
  help the team come to a final decision
\end{enumerate}
