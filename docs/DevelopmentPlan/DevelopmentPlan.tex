\section{Workflow Plan}

The project workflow will be managed using Git, with our code and documentation hosted in our GitHub repository. Our \texttt{main} branch will serve as the primary codebase and will be the branch used for product deployments. To make contributions, developers are required to create branches directly from \texttt{main} and commit any initial changes to their respective branch.

\subsection{Branching Strategy}
We will utilize the following branch categories:
\begin{itemize}
    \item \textbf{feat (feature):} For development on a new feature.
    \item \textbf{bugfix:} For addressing and fixing identified issues within the codebase.
    \item \textbf{chore:} For code changes that support later development, such as refactoring or clean-up work.
\end{itemize}
Additionally, each branch must have a descriptive name that clearly indicates which issue in the GitHub project is being addressed.

\subsection{Issue Tracking and Project Management}
Issues will be categorized based on urgency, from \textbf{P0} (highest priority) to \textbf{P2} (lowest priority), ensuring that critical tasks are addressed promptly. 

The GitHub project board has been configured with the following setup: \textbf{Backlog} $\rightarrow$ \textbf{In Progress} $\rightarrow$ \textbf{Review} $\rightarrow$ \textbf{Closed}. As development progresses, it is the developer's responsibility to keep their assigned issues updated to maintain team visibility on project status.

\subsection{Pull Requests and CI/CD Pipeline}
As part of the new code added to a branch, developers are required to implement test cases to ensure adequate code coverage. Once code is committed, a Pull Request (PR) must be raised to merge the branch into \texttt{main}. 

Our Continuous Integration/Continuous Deployment (CI/CD) pipeline will enforce the following checks before a merge is permitted:
\begin{itemize}
    \item Automated testing and deployment checks.
    \item Linter execution to ensure code meets formatting and quality standards.
    \item Verification that the feature branch is up-to-date with \texttt{main}.
\end{itemize}

\subsection{Code Review Process}
In addition to passing all CI/CD checks, each PR requires a manual review and approval from at least one other group member. The PR comments section will be utilized to trace the iterative process of feedback and the subsequent code changes made to address said feedback.

\subsection{Pull Request Template Requirements}
Each PR must be directly linked to its corresponding issue in the GitHub Project board to maintain traceability. Furthermore, all PRs must adhere to a standardized template that includes:
\begin{itemize}
    \item A comprehensive summary of the changes made.
    \item Sample test cases and step-by-step instructions for the reviewer to verify the code.
    \item Screenshots of the updated UI (if the PR includes user interface modifications).
\end{itemize}

\section{Proof of Concept Demonstration Plan}

At the time of the proof of concept, the application will be able to perform the below actions:
\begin{itemize}
    \item Allow users to set fitness and financial goals
    \item Integrate with fitness technologies to accurately track users' activities
    \item Award users virtual currency based on their activity in an accurate manner
    \item Allow users to invest said virtual currency in a financial market
    \item Provide the user with tooltips and terminology that will help them succeed in real world investing
\end{itemize}

\bigbreak
\noindent The main risks that could hinder the success of the proof of concept are:
\begin{enumerate}
    \item An inability to properly gamify or incentivize compounding habits by rewarding healthy long-term thinking
    \begin{itemize}
        \item To address this risk, the team will be conducting a design thinking exercise.
        This will help with the development of these incentives to make sure that this risk is minimized, as it is critical to the success of the project.
        To prove that this risk is handled, the PoC will implement the incentives discovered by the design thinking exercise to demonstrate that the core thesis of the product is functional.
    \end{itemize}
    \item Improper workout verification leading to any of the following:
    \begin{enumerate}
        \item Rewarding not enough virtual currency
        \item Rewarding too much virtual currency
        \item Users exploiting the tracking system
    \end{enumerate}
    \begin{itemize}
        \item This risk stems from an improper calibration of both the inputs from workout technology, and an improper weighting of the currency system.
        R\&D will be required to fine tune this system and remove this risk
    \end{itemize}
    \item Users being unable to invest the virtual currency that they earn
    \item Failure to integrate with physical fitness technologies
    \item Improper guardrails and teaching points in place
\end{enumerate}

\bigbreak
\noindent If the application is unable to complete the above steps, the team may need to re-analyze the scope of the project.
The single most important risk to meet is the gamification and incentivization of compounding habits.
All other risks are secondary, and the PoC should prioritize the development of the incentives.
In the case that either workouts or investments are being improperly tracked, the team will look into simplifying the system, while keeping the incentives intact.

\section{Expected Technology}

\subsection{Languages and Frameworks}
The application will be developed using the frontend React Native framework (\url{https://reactnative.dev/}) using Typescript (\url{https://www.typescriptlang.org/}) as the coding language. 
Typescript is a common programming language for frontend development with many tools to help the development process. 
Figma (\url{https://www.figma.com/}) mockups will also be used to help the development team create UI concepts and examples for testing and concept design.
\\The backend systems will consist of an SQL relational database through a MySQL server (\url{https://www.mysql.com/}). 
A relational database will allow the development team to keep more concise and organized records to reduce search and loading times for users. 
We will use the Java Spring.io framework (\url{https://spring.io/}) to develop our API. The API will provide the ability to move information securely and smoothly between the application and the database. 
\\The development team will use a Github repository to store the code and support the CI/CD process through development phases. The repository will create a code store for each member to reach and contribute to throughout the process.
Our repository will utilize Copilot AI agents to ensure formatting consistency throughout the codebase. 
The development team will be using various linters such as ESLint (\url{https://eslint.org/}) and the standard linters that come built into the IDE being used like VSCode, JetBrains Intellij and Visual Studio. 


\subsection{External Libraries}
Various external SDKs and APIs will be used to link to external fitness devices.
\begin{itemize}
    \item Connect IQ (Garmin SDK): A major player in the fitness watch company has an open SDK to be used for more accurate data collection and real time updates (\url{https://developer.garmin.com/connect-iq/overview/}).
    \item Strava API: Strava is popular application for runners to track data. The API will allow us to connect to the strava tracking system for users of the app to help track different metrics (\url{https://developers.strava.com/}).
    \item Health Connect API (Android Development Health API): Android provides an API for users to be able to retrieve health data to connect across applications easier (\url{https://developer.android.com/health-and-fitness/health-connect}).
\end{itemize}

\subsection{Technology and External Devices}
The application will rely on the device itself for its basic activity tracker. 
Any additional activity tracking devices like smart/fitness watches, standalone heart rate monitors, pedometers, etc. will be integrated utilizing the intended SDK or API provided by the manufacturer. 

\subsection{Testing}
The development team will use standard unit testing and system testing frameworks like JUnit (\url{https://junit.org/}). 
These tests will be manually prepared by the developers to test different features of the app. 
The development team will also use the frontend testing framework Detox (\url{https://wix.github.io/Detox/docs/introduction/getting-started/}). This will help to provide another layer of verification to the frontend systems.

AI tools will be used for front end development and to a lesser extent
for back end development. Front end components will consists of screens, layouts,
and UI components, of which LLMs generate well. The back end handles fitness data,
virtual currency, and portfolio values, where mistakes are harder to spot, so

The team will use Claude, and GitHub Copilot for code
development. ChatGPT will also be used in for answering small clarifying questions 
and attending to tasks non-code or documentation related.
Finally, GitHub Copilot will also be used to generate an overview of each
pull request to help reviewers understand the changes.

\subsection{Documentation Development}

LLM use for documentation will be minimal. It will be limited mainly to finding
and correcting grammar mistakes, along with preliminary research/brainstorming. The content of each document will be mostly written by
the team. The team will continue to use class templates with the occasional help from Copilot and ChatGPT for documentation.

\subsection{Verification of LLM Output}

Every merge into the main branch requires manual review and approval from one
team member other than the developer who wrote the branch. Reviewers check
that the changes work as intended and that the code is correct, regardless of
whether it was written by a person or generated by an LLM. The Copilot pull
request overview helps reviewers get oriented, but does not replace either
review.

    With the seamless testing, it also allows us to catch and fix any issues right away. Some disadvantages are that it can be tricky to debug and understand at times; if your test suite/coverage is incomplete it can be difficult to implement with the main code.
    \item What disagreements did your group have in this deliverable, if any,
    and how did you resolve them? Answer: Our only disagreement was our difference in preferred stacks for the project. We came into the project with different skills and experience, and we had to come to a compromise on what stack we would use for the project. We resolved this by having a discussion about the pros and cons of each stack, and ultimately decided on a stack that we all felt comfortable with and that would allow us to build the project effectively.
    Another lengthly discussion we had, albiet not entirely a disagreement, was on branch protection, and whether or not we should have branch protection on every branch, and require reviews even for small changes made after they've previously been approved.
\end{enumerate}

\subsection*{Attendance}

\subsubsection*{Expectations}

\begin{itemize}
    \item All team members are expected to attend all scheduled meetings, unless they 
    have an acceptable excuse for missing the meeting
    \item Arrive at least 10 minutes before to the agreed upon location if the 
    meeting is held in person, and at arrive at least 5 minutes before any scheduled 
    virtual meetings to ensure prepardness and that the full meeting time may be 
    utilized effectively
    \item If a team member is unable to attend a meeting, they are expected to notify 
    the rest of the team in the Microsoft Teams groupchat at least 24 hours in advance, unless it is an emergency situation 
    and out of their control
    \item If a team member misses a meeting or misses part of a meeting, they are expected 
    to review the meeting notes and any relevant documents before the next meeting 
    to get caught up on what they missed
    \item If a team member misses 2 meetings in a row without an acceptable excuse or 
    proper communication with the rest of the team, the team will schedule an
    emergency meeting to address this issue. If the issue persists, it will be escalated to the 
    TA and/or instructor for further action
    \item Arriving late to a meeting or leaving early without an acceptable excuse will 
    result in a warning. If this happens more than 3 times, the team will schedule an 
    emergency meeting to address this issue. If the issue persists, it will be escalated to the 
    TA and/or instructor for further action
\end{itemize}

\subsubsection*{Acceptable Excuse}

\begin{itemize}

    car breaks down on the way to a meeting)
    \item Medical appointments that were scheduled in advance and cannot be rescheduled
    \item Medical, personal, or family emergencies
    \item Personal ilness or injury that hinders the teammate's ability from attending

\noindent Unacceptable Excuses:

\begin{itemize}
    \item Technical difficulties during virtual meetings (i.e. internet issues, 
    computer issues, etc.). These can and should be resolved before the meeting 
    starts
    \item Forgetting about a meeting or forgetting to notify the team about 
    a prior conflict
    \item Other course deliverables. These meetings are scheduled in advance and 
    thus should be planned around in order to meet deadlines for all courses
\end{itemize}

\subsubsection*{In Case of Emergency}

\begin{enumerate}
  \item Contact the rest of the team immediately about the emergency (the specific details 
  of the emergency are not required to be shared as they may be personal)
  \item Assess the situation and determine how long this emergency will hinder your 
  progress (i.e. will just miss one meeting, will miss a deliverable deadline, 
  will miss extended time)
  \item Find a replacement/backup team member with extra capacity to cover for you 
  \begin{enumerate}
    \item Meetings - if you have a prominent role in the meeting(s) (i.e. scribe) 
    find and contact a team member that can fill the role of scribe for the missed 
    meeting(s)
    \item Deliverables - if your assigned task is yet to be completed, communicate 
    your progress with the team so they can delegate that responsibility to another 
    team member with extra capacity to complete the task
  \end{enumerate}
  \item When the emergency is resolved and you are able to get back into the project,
  catch up on what you have missed
\end{enumerate}

\subsubsection*{Decision Making} 

\begin{enumerate}
  \item All ideas will be considered and discussed by the team before a decision is reached
  \item The team will first attempt to come to a consensus on a decision as we 
  should all be in agreement and aligned before making impactful decisions
  \item If a consensus cannot be reached, the team will hold a vote on the decision. For an 
  idea to be passed a majority vote of 3 out of 5 members is required
  \item If the team is struggling to decide between options (i.e. they cannot clearly 
  decide where to cast their votes), an unbiased third party will be involved to 
  help the team come to a final decision
\end{enumerate}
